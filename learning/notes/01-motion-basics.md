# 01. モーションの基礎概念

## 3Dキャラクターの構成要素

### スケルトン（骨格）
ボーン（骨）が親子関係で繋がった階層構造。人間の骨格と同じ。

```
Hips（腰）← 全体の基点（ルートボーン）
├── Spine → Spine1 → Spine2 → Neck → Head（体幹〜頭）
│   ├── L-Shoulder → L-Arm → L-ForeArm → L-Hand → 指（左腕）
│   └── R-Shoulder → R-Arm → R-ForeArm → R-Hand → 指（右腕）
├── L-UpLeg → L-Leg → L-Foot → L-Toe（左足）
└── R-UpLeg → R-Leg → R-Foot → R-Toe（右足）
```

**親子関係のポイント:** 親ボーンを回すと、子ボーンも全部ついてくる。
例: 肩(Arm)を前に出す → 前腕(ForeArm) → 手(Hand) → 指 まで全部前に出る。

### メッシュ（見た目）
ボーンにくっついた3Dの形状。このプロジェクトでは簡略化した箱（Box）を使用。
定義場所: `types.ts` の `BODY_PARTS`（約50パーツ）

---

## モーションの2つの方式

### キーフレーム方式（一般的なゲーム）
- Blender、Maya等のツールで事前にアニメーションを作成
- 「フレーム10で腕をこの角度、フレーム20でこの角度」とキーを打つ
- ゲーム中はそのデータを再生するだけ
- メリット: アニメーターが直感的に作れる
- デメリット: 状況に応じた動的な変化が苦手

### プロシージャル方式（このプロジェクト）
- コードで毎フレーム計算して動かす
- 「手をこの位置に持っていけ」→ IKが関節角度を計算
- メリット: 相手の位置、武器の種類に応じて動的にモーションが変わる
- デメリット: パラメータ調整が必要、直感的に作りにくい

## 攻撃モーションの構成要素

### 1. 手の軌道（SwingMotion）
3点で定義される:
- **startPos** — 攻撃開始時の手の位置
- **windupPos** — 振りかぶり到達位置
- **strikePos** — 打撃終了位置

### 2. 体幹の動き（BodyMotion）
| パラメータ | 意味 | 単位 | 正の値 |
|-----------|------|------|--------|
| torsoLean | 胴体の前傾/後傾 | ラジアン | 前傾 |
| torsoTwist | 胴体の左右捻り | ラジアン | 右回転 |
| hipsOffset | 腰の上下移動 | メートル | 上 |
| hipsForward | 腰の前後移動 | メートル | 前 |
| footStepR | 右足の踏み出し | メートル | 前 |
| offHandOffset | 左手の位置補正 | メートル | [前, 上, 右] |

### 3. 時間制御
- `progress`: 0→1 に進行
- `windupRatio`: 振りかぶりと打撃の境目（0.6 = 前半60%が振りかぶり）
- ease-in: 振りかぶりはゆっくり加速
- ease-out: 打撃は最初が速く減速

## 1フレームの処理フロー

```
AI決定「縦振り、パワー80%」
  ↓
createSwingMotion()
  手の軌道3点を計算
  swing-presetsからBodyMotionプリセットをロード
  power × bodyCommitment × gripCommitment でスケーリング
  ↓
毎フレーム updateSwingMotion(dt)
  progressを進める
  手の位置を補間 → IKターゲットにセット
  BodyMotionを補間 → 背骨・腰に適用
  ↓
IKソルバー（3パス）
  手の位置 → 肩・肘の角度を逆算
  関節角度をクランプ（肘5°〜150°）
  足をIKで地面に接地
  ↓
描画
```

## Phase 1: 座標系と3D数学の基礎

### 1-1. 座標系の基本（X/Y/Z軸）

3D空間の位置は `(x, y, z)` の3つの数字で表す。Babylon.js の規約:

- **X軸**: 左右（右が+、左が−）
- **Y軸**: 上下（上が+、下が−）
- **Z軸**: 前後（前が+、後ろが−）

キャラクターが立つ床は `y=0`、頭は `y=1.6` 付近。

### 1-2. 右手系 / 左手系

軸の「向き」の取り決めが2種類ある。違いは **Z軸の向き（前が+か−か）**。

- **右手系**: 手前が+Z、奥が−Z（Blender, Maya, Three.js, Mixamo元データ）
- **左手系**: 奥が+Z、手前が−Z（Babylon.js デフォルト, Unity, DirectX）

→ 右手系のモーションデータをそのまま左手系で使うと **前後が逆** になる。

### 1-3. Y-up / Z-up

「上がどの軸か」の規約も違う。

- **Y-up**: 上が+Y（Babylon.js, Unity, Mixamo出力）
- **Z-up**: 上が+Z（Blender, 3ds Max, FBX内部表現）

Mixamo FBX の生データは Z-up なので Y-up への変換が必要。

### 1-4. ラジアンと度数

3D回転の角度単位は2種類。

- **度数(degree)**: 1周=360°。人間に直感的。
- **ラジアン(radian)**: 1周=2π(≒6.283)。円弧の長さベース。

**変換式:**
```
ラジアン = 度数 × (π / 180)
度数 = ラジアン × (180 / π)
```

**よく出る値:**
| 度数 | ラジアン |
|------|---------|
| 0°   | 0       |
| 90°  | π/2 ≒ 1.5708 |
| 180° | π ≒ 3.1416 |
| 360° | 2π ≒ 6.2832 |

**なぜラジアンを使うのか:** 3Dライブラリの関数(`Math.sin`, `Math.cos`, 回転API)はほぼ全てラジアンを受け取る。微積分や円運動の式がラジアンだとシンプルになるため。コード中は `Math.PI / 4` (=45°) のように書くか `Tools.ToRadians(45)` 等のヘルパーを使う。

## 座標系の違いをモーションに反映する方法（一般論）

モーションデータは**「各ボーンが毎フレームどの位置・どの回転を持つか」の時系列**。座標系が違うデータを使うには、**すべての位置と回転に同じ変換規則を適用する**のが基本。

### ステップ1: どの変換が必要か判定する

| 項目 | 元 (Mixamo FBX) | 先 (Babylon.js) | 必要な変換 |
|------|-----------------|-----------------|------------|
| 単位 | cm | m | ÷100 |
| 上方向 | Z-up | Y-up | 軸入替 |
| 手系 | 右手系 | 左手系 | Z反転 |

一致している項目は変換不要。違う項目だけ処理する。

### ステップ2: 位置データを変換する

ボーンの平行移動（主にルートボーンの移動）に適用。

**スケール変換（cm→m）:**
```
p_new = p_old / 100
```

**軸変換（Z-up → Y-up）:**
```
p_new.x =  p_old.x
p_new.y =  p_old.z    // 元のZ(上)を新しいY(上)へ
p_new.z = -p_old.y    // 元のY(前後)の符号を反転してZへ
```

**ハンドネス変換（右手系→左手系, Z反転方式）:**
```
p_new.x =  p_old.x
p_new.y =  p_old.y
p_new.z = -p_old.z
```

3つを順に合成すれば最終位置になる。

### ステップ3: 回転データを変換する（ここが本質）

モーションの中身はほぼ**ボーンの回転**。回転はクォータニオン `(x, y, z, w)` で表現される。

**軸変換（Z-up → Y-up）:**
クォータニオンの `(x, y, z)` 成分は「回転軸の方向」。位置と同じ規則で入れ替え。
```
q_new.x =  q_old.x
q_new.y =  q_old.z
q_new.z = -q_old.y
q_new.w =  q_old.w    // スカラー成分は変わらない
```

**ハンドネス変換（右手系→左手系, Z反転方式）:**
軸成分のZを反転。さらに**回転の向き**が逆になるので `w` も反転。
```
q_new.x =  q_old.x
q_new.y =  q_old.y
q_new.z = -q_old.z
q_new.w = -q_old.w
```

※ なぜ `w` を反転？ 左手系では「正の回転方向」が逆（右ねじ → 左ねじ）になるため、同じ見た目の回転を表すには回転角の符号も反転する必要がある。

### ステップ4: 階層に沿って適用する

ボーンには親子関係がある。変換の適用範囲は2通り:

- **ローカル回転だけ変換**: 各ボーンの「親から見た回転」に変換を適用。階層は変えない。
- **ワールド座標で変換**: 各ボーンの絶対姿勢を変換してから親子関係を再構築。

一般には前者（ローカル回転だけ変換）で十分かつ破綻しにくい。

### ステップ5: ルートボーンの特別扱い

キャラクター全体の位置・向きは**ルートボーン**が担う。ルートの平行移動と回転だけは「場所」の情報なので、位置と回転の両方を変換する。それ以外の子ボーン（肩・肘・膝など）は多くの場合「親から見た相対回転」だけを持ち、平行移動はゼロ。

### まとめ: モーションに反映する全体フロー

```
元データ（Mixamo FBX, Z-up, 右手系, cm）
   │
   ├─ ① ボーンごとのローカル回転を読み取る
   │
   ├─ ② 回転に「軸変換 + ハンドネス変換」を適用
   │
   ├─ ③ ルートの位置に「スケール + 軸変換 + ハンドネス変換」を適用
   │
   ├─ ④ ボーン階層（親子関係）はそのまま維持
   │
   └─ ⑤ 毎フレーム同じ変換を適用して時系列データを作る
        ↓
   使用先のエンジン（Y-up, 左手系, m）で再生
```

### 補足: 「変換の順序」に注意

スケール・軸変換・ハンドネス変換を合成するとき、**順序を間違えると結果が狂う**ことがある。一般的な安全策は、3つをまとめた1つの**4×4変換行列**を作り、全ボーン・全フレームに同じ行列を適用すること。これで順序の混乱が起きない。

## 1-5. ベクトルの基本（位置・方向・長さ）

### ベクトルとは
3つの数字 `(x, y, z)` の組。**意味の違いで3種類**に使い分ける:

| 用途 | 例 | 意味 |
|------|-----|------|
| 位置ベクトル | `(0, 1.6, 0)` | 空間内の「点」。原点からの位置 |
| 方向ベクトル | `(0, 0, 1)` | 「向き」だけを表す。長さは1に正規化することが多い |
| 変位ベクトル | `(0, 0.5, 0)` | 「ずれ」を表す。A→Bの差分 |

※ 数式上は同じ `(x, y, z)` だが、意味が違うので混同しないことが重要。

### 基本演算

**足し算・引き算:**
```
A + B = (Ax+Bx, Ay+By, Az+Bz)   // 位置 + 変位 = 新しい位置
B - A = (Bx-Ax, By-Ay, Bz-Az)   // A→B の向きと距離
```
→ 「敵の位置 − 自分の位置」で敵への方向ベクトルが得られる。

**スカラー倍（定数倍）:**
```
k × A = (k×Ax, k×Ay, k×Az)
```
→ 方向ベクトルに速度をかければ「移動量」になる。

**長さ（magnitude）:**
```
|A| = √(Ax² + Ay² + Az²)
```
→ ピタゴラスの定理の3次元版。距離計算に使う。

**正規化（normalize）:**
```
Â = A / |A|
```
→ 長さを1にした「純粋な向き」ベクトル。方向だけ欲しいときに使う。

### 内積（dot product）
```
A · B = Ax×Bx + Ay×By + Az×Bz = |A|×|B|×cos(θ)
```
2つのベクトルが作る**角度**を測るのに使う。

- `A · B > 0` → 同じ向き寄り（90°未満）
- `A · B = 0` → 直角
- `A · B < 0` → 逆向き寄り（90°超）

**モーションでの用途:** 「プレイヤーが敵の正面にいるか？」「攻撃が相手の方向に向いているか？」を判定。

### 外積（cross product）
```
A × B = (Ay×Bz - Az×By,
         Az×Bx - Ax×Bz,
         Ax×By - Ay×Bx)
```
2つのベクトルに**直交する新しいベクトル**を作る。

**モーションでの用途:** 「上方向と前方向から右方向を作る」「回転軸を求める」。IKのポールヒント計算でも多用される。

## 1-6. クォータニオン（3D回転の表現）

### なぜクォータニオンが必要か

3D回転を表現する方法は複数ある:

| 方法 | 形式 | 問題点 |
|------|------|--------|
| オイラー角 | (pitch, yaw, roll) の3つの角度 | **ジンバルロック**（特定角度で回転軸が1つ消える） |
| 回転行列 | 3×3の行列（9個の数字） | データが大きい、補間が難しい |
| **クォータニオン** | **(x, y, z, w) の4つの数字** | **ジンバルロックなし、補間が滑らか** |

→ 3Dグラフィックス・モーションでは **クォータニオンが標準**。

### クォータニオンの中身

```
q = (x, y, z, w)
```

意味は「**どの軸 (x, y, z) を中心に、どれだけ (w) 回すか**」を1つの4次元ベクトルにエンコードしたもの。

**軸 `n̂` 周りに角度 `θ` 回す場合:**
```
x = n̂.x × sin(θ/2)
y = n̂.y × sin(θ/2)
z = n̂.z × sin(θ/2)
w = cos(θ/2)
```

※ `θ/2`（半分の角度）が使われるのが特徴。これのおかげで合成がきれいに行える。

### 代表的な値

| 回転 | クォータニオン (x, y, z, w) |
|------|------------------------------|
| 無回転（静止） | (0, 0, 0, 1) |
| Y軸周りに90° | (0, 0.707, 0, 0.707) |
| Y軸周りに180° | (0, 1, 0, 0) |
| X軸周りに90°（前傾） | (0.707, 0, 0, 0.707) |

### よく使う演算

**回転の合成（掛け算）:**
```
q_total = q2 × q1     // 「q1を適用してからq2を適用」
```
→ 注意: **順序が大事**（可換でない）。親→子へ回転を伝えるときに使う。

**補間（slerp: spherical linear interpolation）:**
```
q_mid = slerp(q_a, q_b, t)    // t: 0〜1
```
→ 2つの姿勢の間を滑らかに補間。モーションのキーフレーム間の中割りで必須。

**逆回転（共役）:**
```
q⁻¹ = (-x, -y, -z, w)
```
→ 「元に戻す回転」。座標変換で多用。

### モーションでの使い方

ボーンの姿勢は各フレームで `q_bone = (x, y, z, w)` として保存される。毎フレーム slerp で補間したり、親のクォータニオンと合成してワールド姿勢を求めたりする。

**直接 (x, y, z, w) を手で書くことは稀**で、通常は「軸と角度」「オイラー角」から変換関数で作る（`Quaternion.RotationAxis(axis, angle)` 等）。

## 1-7. ローカル座標とワールド座標

### 2つの座標系

| 座標系 | 基準 | 例 |
|--------|------|-----|
| **ワールド座標** | 世界の原点 `(0,0,0)` | 「キャラクターは地面の中央 `(0, 0, 5)` にいる」 |
| **ローカル座標** | 親ボーン（または親オブジェクト） | 「前腕は肘から見て `(0, -0.3, 0)`（30cm下）」 |

### なぜ2つ必要か

**ローカルで持つメリット:**
- 親を動かせば子も自動的について動く
- 「肘から手首まで30cm」のような**身体構造**を変えずに済む
- 体全体を回転させても、肩→肘→手の関係は崩れない

**ワールドで必要なケース:**
- 当たり判定（剣の先端は世界のどこにあるか？）
- カメラからの見た目（画面上の位置）
- 他のキャラとの距離計算

### 変換の方向

**ローカル → ワールド（下向き伝搬）:**
```
ワールド姿勢 = 親のワールド姿勢 × 自分のローカル姿勢
```
→ ルート(Hips)から順に下って、各ボーンのワールド位置を計算していく。

**ワールド → ローカル（上向き逆算）:**
```
ローカル姿勢 = 親のワールド姿勢⁻¹ × 自分のワールド姿勢
```
→ IKで「手をこのワールド位置に」と指定されたとき、肩・肘のローカル回転を逆算するのに使う。

### モーションデータはローカルで保存される

Mixamo・Blender等が出力するボーンモーションは**ローカル回転の時系列**が基本。理由:

- ボーン構造が違うキャラクター間でも流用しやすい
- 親を動かせば自然に全体が連動する
- データサイズが小さい（平行移動は通常ルートだけ）

→ エンジン側で「ローカル→ワールド」の伝搬を毎フレーム行い、最終的な姿勢を得る。

## 1-8. 座標変換パイプライン（Mixamo → Babylon.js の全体像）

これまでの内容を統合した全体図:

```
┌─ Mixamo FBX（元データ）────────────────────┐
│  - 単位: cm                                 │
│  - 軸: Z-up                                 │
│  - 手系: 右手系                             │
│  - ボーンごとのローカル回転（クォータニオン）│
│  - ルートボーンの位置（ベクトル）            │
└────────────────┬────────────────────────────┘
                 ↓ ① FBXパーサで生データ抽出
                 ↓
┌─ 中間データ（JSON等）───────────────────────┐
│  - 生の数値（変換なし）                      │
└────────────────┬────────────────────────────┘
                 ↓ ② 変換処理
                 │   - 位置: ÷100（スケール）
                 │   - 位置: 軸入替 Z-up→Y-up
                 │   - 位置: Z反転（ハンドネス）
                 │   - 回転: 軸入替
                 │   - 回転: Z反転 + w反転
                 ↓
┌─ Babylon.js 用データ ──────────────────────┐
│  - 単位: m                                  │
│  - 軸: Y-up                                 │
│  - 手系: 左手系                             │
│  - 各ボーンのローカル回転                    │
│  - ルートボーンの位置                        │
└────────────────┬────────────────────────────┘
                 ↓ ③ 毎フレーム適用
                 ↓
┌─ ランタイム処理 ────────────────────────────┐
│  ボーン階層に沿ってローカル→ワールド伝搬    │
│  → メッシュに反映 → 描画                    │
└─────────────────────────────────────────────┘
```

**重要な設計原則:**
- **生データ抽出と座標変換は分離する**（責任分担を明確に）
- **変換は一箇所に集約する**（重複変換・変換漏れを防ぐ）
- **変換行列1つにまとめる**と順序ミスが起きにくい
